visualize & research-viz — a research-to-visualization pipeline, built as Claude Code skills

Skill authoringPrompt engineeringBashHTML/CSS/JS

A pair of custom skills I wrote that turn any substantial research answer into a self-contained, interactive single-file HTML page — all CSS/JS/SVG inlined, no build step, renders offline. research-viz chains a deep-research protocol (fan-out web searches, primary-source fetches, adversarial verification, numbered citations) into visualize, which must derive a fresh visual identity per topic: a design constraint baked into the skill so no two pages look alike.

Case study
  • Skill engineering, not skill usage: progressive-disclosure reference files (patterns, theming, design directions), a neutral starter template, and shell scaffolding scripts the agent invokes — including a retention script driven by a weekly cleanup routine.
  • Production evidence: 85+ generated artifacts over 7 weeks — research reports, engineering deep-dives, architecture explainers, business analysis.
  • An engineering-evolution story: v1 scaffolded a full React + Vite app per run; I re-architected it to emit one dependency-free HTML file, because output you have to host is output you eventually have to clean up.

ado-flow-metrics — flow analytics for Azure DevOps teams, open-sourced with a demo mode

Node · ExpressChart.jsMonte CarloDelivery analyticsOpen source · CI

The tool behind the flow-analytics story on my résumé: WIP aging, PR aging and review state, weekly throughput with outlier detection and attribution, cycle-time percentiles, and Monte Carlo delivery forecasting ("20 tickets: 85% confident by Nov 9") — in one small local app where the Azure DevOps token never leaves the server. npm run demo runs every view on synthetic data with no account. Code at github.com/jacobv25/ado-flow-metrics.

Case study
  • Built for a real team, then generalized: my 20-engineer team had boards that showed status but not age. This made aging visible, and the WIP-limit and PR-aging policies it surfaced are the ones the team adopted. The open-source version swaps the live client for a seeded fake behind the same request seam, so demo mode exercises every real route.
  • Forecasting without estimates: Monte Carlo sampling over the team's own weekly throughput gives p50/p70/p85/p95 finish dates; outlier weeks are flagged with a Tukey IQR fence (MAD fallback) and explained from the items in the bucket. Assumptions are printed on the page, not hidden.
  • Planned before coded, tested after: each feature started as a written design doc with options and trade-offs (in the repo). Pure, dependency-free analytics modules under Node assert tests; CI runs them on two Node versions and boots demo mode against every route.

SPEEDHELL — a browser bullet-hell, shipped through a builder/critic/referee gauntlet

Canvas2D · ES modulesMulti-agent orchestrationHeadless verificationZero dependencies

A Psikyo-style vertical bullet-hell shmup in the "speed hell" lineage — fast aimed bullets, speed-kill scoring — running in the browser with zero dependencies: Canvas2D, ES modules, no build step. Playable now at jacobv25.github.io/speedhell, code at github.com/jacobv25/speedhell. The shipped successor to the shmup-claude plan below — and 1CC'd by its author.

Case study

matchbook — an agent-native CLI, plus an Android sensor to feed it

GoSQLite · FTS5Kotlin · ComposeAgent-native design

A Go CLI (~2.2k lines, cobra + SQLite full-text search) that mirrors a messaging-app data export into a local database and exposes compound, token-efficient commands (needs-reply, stalled, stats) with --json on every read — wrapped in a SKILL.md so an agent can drive it in natural language. A companion Android app uses a NotificationListenerService to stream fresh message events to the CLI's ingest server, solving "the official export takes days."

Case study
  • Judgment over capability: the obvious route was reverse-engineering a private API — a ToS violation. Instead the tool mirrors a proven architecture against the official on-disk export, and the Android sensor only reads notifications the OS already delivered to my own device.
  • Agent-native by design: compound commands minimize agent turns; JSON output eliminates parsing guesswork; AI-assisted commands (summarize, suggest) are gated behind explicit flags and produce drafts for human review, never auto-replies.
  • Tested: go test coverage on the export parser and store, including full-text search and idempotent re-ingest; all format assumptions isolated to one package.

undertow — an anti-doomscrolling Android app

Kotlin · ComposeAccessibilityServiceBehavior designJUnit

An AccessibilityService watches scroll events inside feed apps (Instagram, Facebook, TikTok, YouTube) and interrupts a continuous scroll session past a configurable threshold with a full-screen breathing pause — two exits: "I'm done" (counted as a win) or an ever-shrinking snooze. Friction, not a hard block. Fully public: github.com/jacobv25/undertow.

Case study
  • Behavior-first design: hard blocks get uninstalled, so every choice favors sustainable friction — snoozes shrink 60s → 30s → 15s, leaving the app on your own is logged as a win rather than an escape, and a minute of stillness resets the clock so intentional use isn't punished.
  • Surface-level detection: regular YouTube is free; only the Shorts surface counts, detected by walking view resource ids from the scroll event's source node. The doomscroll loop is the target, not the app.
  • Tested core, honest privacy: the session state machine is pure Kotlin under JUnit; nothing scrolled past is read — only scroll events and their app are counted, on-device, 30-day retention.

ose-vtt — a 16-path design exploration judged by an LLM panel

Multi-agent orchestrationLLM-as-judgeAgent-safety architecture

Before writing any code for an AI-assisted virtual tabletop, I ran the design space through a multi-agent process: 16 candidate designs generated across a 4×4 matrix (AI ambition × human authority), each scored by three distinct judge personas (domain purist, software architect, product/UX), then leaderboarded and synthesized — using convergence across independent paths as the signal.

Case study
  • Safety as data model: the winning architecture makes the AI structurally incapable of touching shared state — every agent action is a staged command requiring human commit, with no canonical setter exposed to the agent layer.
  • "The LLM never produces a number": all dice, math, and rules resolution live in a deterministic engine; the agent narrates and proposes. Every result carries a provenance object (dice, seed, formula, rule cited).
  • Output: a full design report with MVP scope, trade-offs, and a "validate first" list — the kind of artifact I'd want before funding a build.

Sandboxed autonomy — running a permissionless agent safely

Apple containerDockeriptables · ipset · dnsmasqInfra

To run Claude Code fully autonomously (no permission prompts) without giving it my machine, I built a sandbox: an isolated Linux microVM via Apple's container on Apple Silicon, with the project bind-mounted read-write and everything else walled off behind a network egress allowlist.

Case study
  • The interesting problem: a naive IP allowlist fails for CDN-fronted domains. My firewall runs dnsmasq locally — when the agent resolves an allowed domain, the freshly-resolved IP is added to an ipset that iptables permits. Robust to IP rotation, no broad CIDR grants. IPv6 is dropped and AAAA records stripped so nothing bypasses the IPv4 allowlist.
  • Verified, not vibes: the README documents tested behavior — allowed domains reachable; example.com, google.com, and raw IPs blocked — plus honest caveats (required capabilities, fail-closed behavior, version compatibility).
  • Why it matters: autonomous agents are only as trustworthy as the boundary you run them inside. I built the boundary.

A daily launchd job that drives headless Chrome through a government web portal to check whether a filing window has opened, clicking through interstitial prompts and classifying the outcome. On eligibility it sends a phone push whose message is literally "Open Claude Code and say 'file it'" — the automation exists to hand a task back to an agent at exactly the right moment.

Case study

  • Self-terminating: success touches a sentinel file so it never fires twice, and the header comment documents its own teardown. Automation with a lifecycle, not a zombie cron job.
  • Defensive scraping: reasons about rendered-vs-hidden DOM text to avoid false positives, and polls frames to find the embedded workflow iframe rather than assuming page structure.

02 How I work with agents

Patterns that repeat across everything above — the practice behind the projects.

Context engineering

Layered CLAUDE.md / AGENTS.md constitutions per workspace and per app: one big idea up front, progressive disclosure for detail, guardrails stated as enforceable rules, and documented gotchas. A codebase an agent can be productive in is a codebase a new engineer can be productive in.

Agent-native interfaces

Tools designed for an agent as a first-class user: --json everywhere, compound commands that minimize turns, skills wrapping CLIs in natural language, and structured specs instead of freeform code generation.

Bounded autonomy

Autonomous sessions run inside boundaries I built and verified: sandboxed microVMs with DNS-aware egress allowlists, staged-commit data models where the AI can propose but never silently mutate, and human review gates on anything outward-facing.

Verification loops

Typecheck-and-test gates, 1-minute test knobs so end-to-end behavior is checkable on demand, headless auto-playtesting, and self-monitoring automations that report their own failures. If the agent can't verify it, it isn't done.

Multi-agent orchestration

Fan-out generation with judge panels and synthesis for design work; parallel research with adversarial verification and citations for analysis. Convergence across independent agents is signal; a single confident answer is not.

Ship the evidence

Every exploration ends in an artifact — a cited report, an interactive visualization, a design doc with a leaderboard, a README with a verified-behavior table. Work that can't be shown might as well not exist.
